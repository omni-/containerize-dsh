Maintain this canonical skill in `skills/dsh-work/` in the `containerize-dsh`
repository. Installed Codex and Claude Code copies are generated by
`python scripts/install_workflow.py`; do not edit those generated copies.

This skill runs on the **HOST**. `dsh-task` is the source of truth for task state,
validation, recovery, Git transfer, integration, and cleanup. Do not reimplement
its lifecycle in shell, Python, Docker, Git plumbing, transcript parsers, or direct
imports from `dsh_task.py`.

If `dsh-task` is not on PATH, read `references/launcher.txt` and invoke the
installed launcher from there.

## Rules

1. Resolve the requested task with `dsh-task show <id>`.
2. Read only the target repository instructions needed for the requested action.
3. Invoke the smallest matching `dsh-task` command(s).
4. Treat helper refusals and warnings as authoritative. Do not work around them by
   mutating manifests, task records, Docker resources, Git refs, or helper internals.
5. Keep model-side inspection bounded. Do not reconstruct full historical sessions,
   parse old transcripts, enumerate ignored/build trees, or print large helper logs
   unless the user specifically asks for that evidence.
6. Never run concurrent operations on the same task.

## Intent mapping

### Review

Run:

```text
dsh-task export <id>
```

If export reports untracked files, inspect only the reported names. Use
`--include-untracked` only when they all belong to the task; otherwise report the
blocker instead of inventing file-selection machinery.

Review the exported revision against the base recorded by the task. Use normal
repository review tools and run only relevant checks. Write a concise review report
to a temporary/local file, then record it exactly as instructed by `dsh-task show`
or the export output:

```text
dsh-task reviewed <id> --revision <oid> --report <file>
```

Do not fix implementation findings during review unless the user separately
requests a fix.

### Continue work

```text
dsh-task resume <id>
```

Give the user the resulting URL when useful. Do not manipulate the sandbox through
Docker or the lower-level launcher.

### Integrate

Ensure the current export has a review recorded, then run:

```text
dsh-task prepare <id>
```

Inspect and test the prepared worktree/revision reported by the helper. Put the
actual commands, outcomes, and any limitations in a concise checks file. If the
prepared result is acceptable, run:

```text
dsh-task finalize <id> --checks <file>
```

If `prepare` or `finalize` refuses, stop and report the refusal. Do not repair task
metadata, bypass dirty/moved-target checks, or synthesize an alternate integration
path.

### Clean up

Only clean up when the user requests it. After requested integration use:

```text
dsh-task cleanup <id> --require-integrated
```

For standalone cleanup use:

```text
dsh-task cleanup <id>
```

If cleanup refuses, report the blocker rather than deleting resources manually.
Never broadly prune Docker resources.

### Discard

Only when the user explicitly asks to discard the task's container work, run:

```text
dsh-task discard <id>
```

Discard is destructive and requires the user's interactive `y` confirmation. Do
not pipe or auto-answer that confirmation. If interactive input is unavailable,
print the command for the user to run.

## Output discipline

Prefer terse summaries of the helper's result: task/revision, findings, checks,
and blockers. Large logs belong in files, not in model context. `docs/tasks.md` is
reference documentation for humans; consult it only when a helper message is
unclear, not as a second workflow to execute manually.
